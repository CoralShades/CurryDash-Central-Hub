**3/3/2026** Updated Description

We need to ensure that when a Food Item is deleted or marked inactive, it does not leave "broken links" or "ghost items" in the system. This affects three major areas: **Packages (Combos)**, **Active User Carts**, and **Checkout validation**.

#### 1. Package "Unassign"

* Triggered when a food item is deleted or marked as inactive.

    * User notification:  
      **Headline:** `Warning: This item is linked to active packages`
    
        **Body**: `You are attempting to [delete/deactivate] "[Food Item Name]." This item is currently a component of the following packages:`

    
    
        `-Package 01`

    
    
        `-Package 02`

    
    
        `If you proceed, this item will be automatically delinked from these packages.`

    
    
        Actions: `Proceed`, `Cancel`

    
    
* Remove all references from associated packages. The system must automatically set the **Package status** to `Incomplete/Inactive` and notify the merchant via the dashboard.
* **Edge Case:** If a Package (e.g., "Lunch Deal") requires exactly 3 items and removing this item drops it to 2

#### **2. Active Customer Carts**

* **Action:** Do not silently remove the item (which confuses users). Instead, flag the item as `UNAVAILABLE`.
* **UI Requirement:** In the Cart view, the item should be greyed out with a message: _"This item is no longer available."_ \* **Constraint:** The "Checkout" button must be disabled until the unavailable item is removed.

#### **3. Ongoing/Placed Orders (The "Snapshot" Rule)**

* **Requirement:** Orders that are already "Accepted," "Preparing," or "Completed" **must not change**.
* **Logic:** Ensure the `Order_Details` table stores hardcoded strings for `item_name` and `price_at_time_of_purchase` rather than just a foreign key. This ensures historical receipts remain accurate even if the original item is deleted.

---

### **Acceptance Criteria**

* Deactivating a dish removes it from all active "Curry Dash" meal bundles/packages.
* If associated package becomes "Empty" or "Incomplete" due to a deletion, it is hidden from the storefront.
* A user with an active cart cannot pay for an item that was deactivated few minutes ago.
* Admin receives a warning popup before deleting an item

**Critical**: Conduct full end-to-end (E2E) regression testing of the order placement flow across both web and mobile platforms.

## Description

Implement a dedicated detail page that allows the Admin to view and modify all aspects of a vendor-created package, including selection rules and pricing overrides.

**User Story:**

> As an **Admin**, I want to **view and modify all configuration steps of a package**, including its selection rules and item assignments, so that I can audit vendor settings and make necessary changes for compliance or optimization.

### Description

This detail page must emulate the vendor's multi-step creation wizard in a read/write format for the Admin. It must handle complex components like selection rules and individual item pricing overrides, which are critical to the package's functionality.

### UI/UX Requirements

* **Access:** Accessed by clicking the "Edit" button from the main management dashboard.
* **Display:** The page should use a tabbed interface or collapsible sections mirroring the vendor's creation flow:

    1. **Basic Info:** Read/Write fields for Name, Description, Hero Image, and **Base Package Price**.
    2. **Selection Rules:** **Critical Section.** Display the categories defined by the vendor (e.g., "Choose 2 Vegetarian Curries from 8 options"). Admin can modify the min/max selections and review extra charges.
    3. **Food Item Assignment:** **Critical Section.** List all Food Items (associated with that restaurant) currently assigned to the package categories. Admin can remove items or assign new ones via a search interface.
    4. **Scheduling & Limits:** Read/Write fields for Availability Schedule, Publication Status, and Ordering Limits.
    
* **Preview Integration:** Must include a button to launch the **Interactive Customer View Preview** to test changes before saving. **TBD**

### Acceptance Criteria

1. **Rule Modification:** The admin must be able to change the minimum and maximum selection limits for any defined category (e.g., change "Choose 2" to "Choose 3") without breaking the package logic.
2. **Price Overrides:** Changes to the **Base Price** or item-specific pricing overrides must be validated and saved correctly.
3. **Save/Publish:** An explicit **Save Changes** button must be present. Saving a modification to an _Active_ package should require an admin confirmation pop-up.
4. **Audit Trail:** Every time an Admin modifies and saves a package, a record must be added to an internal audit log noting the Admin User ID, time, and fields changed.

## Description

Implement the deletion function and secondary management tools (duplication and analytics view) for packages within the Admin Dashboard.

**User Story:**

> As an **Admin**, I want to **permanently delete packages or quickly duplicate them** for new campaigns, and **view basic performance data**, so that I have full lifecycle control over all offerings.

### Description

This ticket covers high-impact administrative functions: permanent deletion and quick duplication/editing. It also introduces the necessary link to package performance analytics.

### UI/UX Requirements

* **Deletion:**

    * **Location:** Available via the "Action" column in the main dashboard (Ticket 1) and on the detail page (Ticket 2).
    * **Warning Modal:** Deletion must trigger a confirmation modal asking the Admin to type the package name to confirm permanent removal.
    
* **Duplication:**

    * **Location:** Available via the "Action" column in the main dashboard.
    * **Workflow:** Clicking "Duplicate" instantly creates a new package with the status set to **Draft**. The name should be appended with " - Copy" (e.g., "Family Pack - Copy").
    
* **Analytics Link:**

    * **Location:** A dedicated button or section on the Package Detail page (Ticket 2).
    * **Functionality:** Links to a read-only analytics view showing the package's performance (e.g., total orders, revenue generated, most popular selections).
    

### Acceptance Criteria

1. **Deletion Integrity:** Deleting a package permanently removes it from the database and ensures all linked data (such as item assignments) is also decoupled or cleaned up. **Critical:** This action cannot be reversed.
2. **Duplication Accuracy:** The duplicated package must retain the original's _entire_ configuration, including selection rules, assigned items, and pricing, with the status correctly set to **Draft**.

    


3. **Order History Check:** The system must prevent deletion if the package has any active, pending, or processing orders. A package can only be deleted if its status is **Draft** or if all its past orders are completed/archived.

Vendor **must provide either ABN or TFN** to register their business in curry dash.

**ABN:**

* Length: Always 11 digits.
* Structure: Two leading check digits followed by a 9-digit unique identifier (e.g., 36  
  123 456 789).
* No Letters: Contains only numbers, no letters.
* First Digit: The first digit can never be zero (0).
* Check Digits: The first two digits are derived using a specific modulus 89 algorithm to

**TFN:**

* Length: Always 9 digits for modern numbers.
* Structure: An 8-digit number plus a single check digit.
* Display: Often shown as xxx xxx XXX (three groups of three) on documents, but  
  as a continuous 9-digit string in systems.

## Description

Problems with deleting food item or package records

### 1. Database & System Errors

* **Orphaned References:** Packages or "Combos" that were linked to that item ID will now point to a non-existent record, often causing the entire package to fail to load.
* **API Crashes:** If your frontend (App/Web) tries to fetch details for a deleted ID still sitting in a user's "Recent Orders" or "Favorites," it can trigger **500 Internal Server Errors**.
* **Null Pointer Exceptions:** Code logic that expects a price or name to exist for every item in a cart will break when it encounters a "Null" value where the deleted item used to be.

### 2. Broken Checkout Experience

* **Cart Invalidation:** Customers who added the item to their cart hours ago will encounter errors at checkout. Instead of a helpful "Item unavailable" message, the system may simply prevent the order from being placed.
* **Phantom Packages:** A "Family Bundle" might still appear on the menu, but when a user clicks it, it appears empty or refuses to be added to the cart because a required component (the deleted item) is missing.

### 3. Destruction of Business Intelligence

* **Lost Sales History:** Deleting an item often removes it from historical sales reports. You lose the ability to see how many of those items were sold in previous months.
* **Inaccurate Accounting:** If a manager looks at total revenue for the year, the "Sales by Item" report will no longer balance with the "Total Revenue" because the data for deleted items has vanished.

### 4. Operational & SEO Risks

* **No "Undo" Button:** If a vendor deletes a complex item (with multiple photos, descriptions, and 20+ modifier options) by mistake, it is gone forever. They must manually recreate it from scratch.
* **Broken Web Links:** Any direct links to that food item (from social media ads, QR codes, or Google Search) will lead to a **404 Not Found** page, hurting the restaurant's professional image and SEO ranking.
* **Loss of Reviews:** If your platform allows users to review specific items, deleting the item usually deletes all the positive "Social Proof" associated with it.

### 5. Inventory & Vendor Friction

* **Stock Tracking Gaps:** If the item was linked to raw ingredients or inventory management, deleting it can leave "ghost stock" in the system that isn't being tracked or depleted correctly.
* **Notification Failures:** Without a "Status" change, the system can't automatically notify other stakeholders (like the kitchen or delivery partners) that a specific item is no longer on the menu.

---

## Description

To prevent reaching storage limits and to optimize application performance, we need to implement a compression mechanism for all images uploaded to the platform (e.g., restaurant logos, menu items, and delivery proof). Currently, high-resolution uploads are consuming significant storage and slowing down image rendering on the user-facing app.

### **Acceptance Criteria**

* **Compression Trigger:** Compression must occur automatically upon upload before the file is saved to permanent storage.
* **Size Limit:** All images should be compressed to a maximum size of **500KB** without significant loss of visual quality.
* **Resolution Scaling:** If an image width exceeds **1200px**, it should be downscaled while maintaining the original aspect ratio.
* **Supported Formats:** The feature must support `.jpg`, `.jpeg`, and `.png` files.
* **Metadata Stripping:** Remove unnecessary EXIF data (GPS coordinates, camera info) to further reduce file size and protect privacy.
* **Fallback:** If compression fails, the system should log an error but still allow the upload if the original file is under a safety limit (e.g., 2MB).

## Description

Implement an administrative interface to view and modify the "Standard Weekly Delivery Days" for any restaurant, enabling central control and auditing of logistics schedules.

**User Story:**

> As an **Admin/Super Admin**, I want to **view and override any restaurant's weekly delivery schedule**, so that I can correct errors, enforce operational standards, or coordinate with global courier changes without requiring vendor involvement.

### Extra Descriptive Description

Centralized control is necessary for operational consistency. This ticket provides Admin users with the same interface implemented for the seller [https://coralshades.atlassian.net/browse/CAR-96](https://coralshades.atlassian.net/browse/CAR-96)  but accessible via the Admin Dashboard's Vendor Management section. This feature requires robust security checks and an audit trail, as overriding a seller's logistics settings is a high-impact action.

### UI/UX Requirements (Admin Dashboard)

* **Location:** Integrated into the **Vendor/Restaurant Management** detail page (e.g., a "Logistics" tab or section on the individual restaurant's profile page).
* **Interface:** An identical visual interface to the seller's view: seven toggleable buttons/checkboxes (Mon-Sun) labeled **"Admin Override: Weekly Delivery Days."**
* **Visibility:** The Admin must also see the date/time of the **last change** and the user (Admin or Seller) who made that change.
* **Saving:** A dedicated **"Apply Admin Delivery Schedule"** button.
* **Warning Banner:** A banner above the interface stating: "Changes here **immediately override** the Vendor's self-configured settings."

### Backend & Audit Requirements

* **Single Source of Truth:** The Admin interface must read and write to the _same_ `delivery_days_of_week` field used by the seller to avoid conflicting data models.
* **Access Control:** Strict role-based access control must ensure that only users with `Admin/Super Admin` roles can view and modify this field.
* **Audit Trail (Mandatory):** Every time an Admin modifies and saves a restaurant's delivery schedule, a record must be added to a system audit log noting:

    * **Action:** `Restaurant Delivery Schedule Updated`
    * **Restaurant ID:** \[ID of the affected restaurant\]
    * **Admin User ID:** \[ID of the Admin making the change\]
    * **Previous Value:** (e.g., `['M, W, F']`)
    * **New Value:** (e.g., `['M, T, W, Th, F']`)
    
* **Immediate Propagation:** Changes made by the Admin must propagate instantly, updating the seller's view (for transparency) and immediately filtering the customer-facing delivery slot selection.

### Acceptance Criteria

1. **Override Functionality:** An Admin must be able to successfully update a restaurant's weekly delivery schedule, and this change must be validated and reflected instantly on the customer-facing app.
2. **Audit Log Validation:** Any successful change made by an Admin must be logged in the system audit trail, including the identity of the Admin.
3. **Seller Transparency:** When the seller views their Delivery Schedule, the interface must display a banner if the last change was made by an Admin (e.g., "Note: Your current delivery schedule was last updated by a System Admin on \[Date\]").
